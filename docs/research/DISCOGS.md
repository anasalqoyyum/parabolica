## Decision

The API supplies the data for the desired Mp3tag-style workflow: select an album's files, search once, choose a specific release, review and map its tracklist to the selected files, then stage chosen fields for the whole group. Public lookup worked without an Authorization header and is the selected initial access path. Authentication is deferred unless access requirements change. Search is text and identifier lookup, not audio fingerprinting, so the user must confirm the result.

The main technical caution is identity. A Discogs master release groups related editions, while a release is one specific pressing or digital edition. Use the release endpoint for tag fields and track order. Use its master only to browse related versions. Discogs says a master may contain releases whose tracklists vary, sometimes radically. [Master Release guidelines](https://support.discogs.com/hc/en-us/articles/360005055493-Database-Guidelines-16-Master-Release)

Listed metadata has a CC0 copyright/database-rights grant, which permits permanent copies and tagging. The owner-approved model distinguishes durable local metadata from fresh, attributed API source previews. Current first-party terms also distinguish the independently CC0-licensed monthly data dump, but no dump index is needed for the selected REST workflow. Discogs images remain Restricted Data; public access alone does not establish permanent embedding or sidecar permission. Embedding has been withdrawn and Discogs sidecars are not part of the selected art path. The [decision](DISCOGS_INTEGRATION_DECISION.md#remaining-input) records no remaining external input for the revised investigation scope.

## API sequence

| Request | Use |
| --- | --- |
| <code>GET /database/search</code> ([API docs](https://www.discogs.com/developers#page:database,header:database-search)) | Search by artist and release title, or narrow with identifiers such as barcode or catalog number. Set <code>type=release</code> for editions or <code>type=master</code> to find a group of editions. |
| <code>GET /releases/{release_id}</code> ([API docs](https://www.discogs.com/developers#page:database,header:database-release)) | Fetch the chosen edition's full metadata, tracklist, credits, and image list. |
| <code>GET /masters/{master_id}</code> ([API docs](https://www.discogs.com/developers#page:database,header:database-master-release)) | Fetch a group's overview, including <code>main_release</code>, <code>most_recent_release</code>, tracklist, and images. It is not edition-level data. |
| <code>GET /masters/{master_id}/versions</code> ([API docs](https://www.discogs.com/developers#page:database,header:database-master-release-versions)) | Browse the group's editions, then fetch the selected result through <code>/releases/{release_id}</code>. Responses are paginated. |

I verified these calls against the live API on the research date. A search with <code>artist=Rick Astley</code>, <code>release_title=Never Gonna Give You Up</code>, and <code>type=release</code> returned release candidates, each with an ID, summary fields, <code>master_id</code>, and <code>resource_url</code>. The barcode <code>5012394144777</code> returned eight results across pages, so a barcode helps but does not uniquely identify an edition. Search results can have empty <code>thumb</code> and <code>cover_image</code> values even when the full release response has images. Fetch the release after the user chooses a candidate. [Example search response](https://api.discogs.com/database/search?artist=Rick%20Astley&release_title=Never%20Gonna%20Give%20You%20Up&type=release&per_page=2), [barcode search response](https://api.discogs.com/database/search?barcode=5012394144777&type=release&per_page=1)

Search and master-version responses include a <code>pagination</code> object with <code>page</code>, <code>pages</code>, <code>per_page</code>, <code>items</code>, and, when more results exist, <code>urls.next</code> and <code>urls.last</code>. Validate the API origin and expected route before following the returned next URL or attaching credentials. Do not assume the first page contains every candidate. The recorded samples returned 71 release results and 67 master versions; following the returned versions URL reached page 2. [Example master-version response](https://api.discogs.com/masters/96559/versions?per_page=2)

## Release identity and tag mapping

The release response separates the album title from the artist credits. Search results often put both into a display <code>title</code>, such as <code>Rick Astley - Never Gonna Give You Up</code>; do not copy that combined string into the album tag.

| Discogs fields | Suggested local mapping | Cautions |
| --- | --- | --- |
| Release <code>title</code> | <code>ALBUM</code> | Use the selected release title, not the combined search-result display title. |
| Release <code>artists[]</code> | <code>ALBUMARTIST</code>, if the file format supports it | Preserve each credit's <code>name</code>, <code>anv</code>, <code>join</code>, and Discogs artist ID. <code>anv</code> is the way the artist is credited on that release and can differ from the artist's canonical name. Keep the displayed join text. [Artist guidelines](https://support.discogs.com/hc/en-us/articles/360005054753-Database-Guidelines-2-Artist) |
| Track <code>title</code> and optional track <code>artists[]</code> | <code>TITLE</code> and per-track <code>ARTIST</code> | Track-level artists may be absent when all tracks share the release artist. For compilations, do not copy an album-level <code>Various Artists</code> credit over track artists when Discogs supplies individual credits. [Tracklisting guidelines](https://support.discogs.com/hc/en-us/articles/360005055373-Database-Guidelines-12-Tracklisting) |
| Track <code>position</code> | <code>TRACKNUMBER</code>, <code>DISCNUMBER</code> when the position parses unambiguously; optionally preserve raw position in a custom field | Positions can be <code>1</code>, <code>1-1</code>, <code>A1</code>, <code>B2</code>, or just <code>A</code>. Do not sort them as plain strings or assume all positions are numeric. |
| <code>year</code>, <code>released</code>, <code>country</code> | Year/date and an optional custom country field | Values can be absent or partial. A live response had <code>released: "1987-07-00"</code>; do not invent a day. |
| <code>labels[].name</code>, <code>labels[].catno</code> | <code>LABEL</code>, <code>CATALOGNUMBER</code> | Multiple labels and catalog numbers can occur. Let the user choose how they map rather than silently discarding all but the first. |
| <code>genres[]</code>, <code>styles[]</code> | <code>GENRE</code> and a separate custom style field | Keep Discogs genres and styles distinct. The API returns arrays; a file format may encode multiple values differently. |
| <code>extraartists[]</code>, track <code>extraartists[]</code> | Optional credit fields such as composer or producer | Release credits and per-track credits have different scope. Do not merge all credits into <code>ARTIST</code>. |
| <code>notes</code>, <code>identifiers</code>, <code>data_quality</code> | Preview or optional fields | Notes may explain unusual ordering or missing printed durations. Identifiers can help reimport, but are not proof that a match is right. |

A concrete release response for <i>Never Gonna Give You Up</i> has <code>title: "Never Gonna Give You Up"</code>, <code>country: "UK"</code>, <code>released: "1987-07-00"</code>, label <code>RCA</code> with catalog number <code>PB 41447</code>, format <code>Vinyl</code> with quantity <code>1</code>, genres <code>Electronic</code> and <code>Pop</code>, style <code>Euro-Disco</code>, and <code>master_id: 96559</code>. It also includes track-level positions <code>A</code> and <code>B</code>, release credits, and an image array. [Release 249504 response](https://api.discogs.com/releases/249504)

For a two-CD example, release 1890689 has <code>formats: [{"name":"CD","qty":"2",...}]</code> and track positions from <code>1-1</code> through <code>2-9</code>. Its release metadata includes Japan, the date <code>2003-05-28</code>, catalog number <code>WPCR-11616~7</code>, genres <code>Rock</code> and <code>Blues</code>, and styles <code>Hard Rock</code> and <code>Blues Rock</code>. [Release 1890689 response](https://api.discogs.com/releases/1890689)

### Tracklist rows are not always audio files

The API returns an ordered <code>tracklist</code> array. Its JSON field is spelled <code>type_</code>; observed values include <code>track</code>, <code>index</code>, and <code>heading</code>. The recorded King Crimson <i>Lizard</i> response contains an <code>index</code> row with seven nested <code>sub_tracks</code>, including empty durations. This supersedes the earlier observation of a flat response. Drexciya's <i>Bubble Metropolis</i> has <code>heading</code> rows with empty positions and durations. Discogs defines an index as a musical work grouping movements or parts; a heading labels a descriptive section. Neither should automatically become a playable file row. Preserve the hierarchy and require review when the local rip combines or splits movements. [Release 1156598 response](https://api.discogs.com/releases/1156598), [release 6061 response](https://api.discogs.com/releases/6061), [tracklist index and heading rules](https://support.discogs.com/hc/en-us/articles/360005055373-Database-Guidelines-12-Tracklisting)

Discogs' position guidance includes <code>A1</code>, <code>A2</code>, <code>B1</code>, <code>B2</code> for sides and <code>1-1</code>, <code>1-2</code>, <code>2-1</code> for multiple CDs. A single track per vinyl side may be numbered just <code>A</code> and <code>B</code>. Preserve API order and raw positions. Derive disc and track numbers only when the representation is clear. [Track positions](https://support.discogs.com/hc/en-us/articles/360005055373-Database-Guidelines-12-Tracklisting)

Durations are optional and may be absent or empty. Even a populated duration is not necessarily printed on the release: release 249504's notes say the durations do not appear on the physical release, while the API still returns <code>3:32</code> and <code>3:30</code>. Discogs allows durations to be entered from timings, and says they should be measured from the exact edition. Show durations as a review aid. Do not use them as authoritative file lengths or silently fill missing values. [Release 249504 response](https://api.discogs.com/releases/249504), [duration guidelines](https://support.discogs.com/hc/en-us/articles/360005055373-Database-Guidelines-12-Tracklisting)

Track listings can include bonus tracks, index tracks, hidden tracks, non-audio items, or credits only in release notes. Editions in one master can differ. A user should review the chosen edition's track order and file mapping before writing. The API does not guarantee a perfect match or a complete listing.

## Artwork: API behavior and rights

The selected release's <code>images[]</code> entries include <code>type</code> (<code>primary</code> or <code>secondary</code>), <code>uri</code>, <code>resource_url</code>, <code>uri150</code>, <code>width</code>, and <code>height</code>. A primary image is the natural preview default; allow the user to choose a secondary image. In the recorded examples, release 1890689 had a 300x299 primary and a 600x600 secondary; release 249504 had a 600x600 primary. The API does not promise a particular resolution or even that an image exists. <code>uri150</code> is the thumbnail. Use returned URLs on the validated image origin; do not assume the search result's thumbnail is populated or send it API credentials. [Release 1890689 response](https://api.discogs.com/releases/1890689), [Release 249504 response](https://api.discogs.com/releases/249504), [Release API docs](https://www.discogs.com/developers#page:database,header:database-release)

The recorded <code>HEAD</code> request to release 249504's first <code>i.discogs.com</code> image URL returned <code>200</code>, <code>image/jpeg</code> and content length 68,934 without authorization. This confirms reachability for that URL, not an image-byte download or decoder check. Its CDN response included <code>Cache-Control: public, max-age=31536000</code>. This HTTP cache header is not permission to keep or embed the image for a year.

Discogs' API terms classify images as Restricted Data. The terms grant a limited personal, non-transferable, revocable license to use Restricted Data in applications, but forbid transferring it to third parties and using it commercially. They also say Content must not be displayed more than six hours behind Discogs and must not be stored longer than needed for the service. This is not a universal six-hour cache allowance. The listed metadata is CC0, but the broader API wording does not explicitly exempt exported tags or images. Durable local metadata, permanent embedded art and persistent sidecar art therefore have separate decisions in [DISCOGS_INTEGRATION_DECISION.md](DISCOGS_INTEGRATION_DECISION.md). Sidecars are not automatically exempt because they are easier to delete.

Discogs' image guidelines say user submissions must be public domain, licensed CC0 by the rights holder, already CC0, or qualify for the stated fair-use purposes of critical commentary or resale of a physical product. Those rules govern images uploaded to Discogs; they do not give an API consumer a blanket right to reuse a returned image. The same guidelines say images must depict the exact release and warn users not to download an image from Discogs and re-upload it. [API Terms of Use, last updated 2025-05-27](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use), [Image guidelines](https://support.discogs.com/hc/en-us/articles/360005006874-Database-Guidelines-13-Images)

For this personal client, any retained Discogs artwork preview stays separate from durable writing; Discogs embedding is no longer pursued. User-supplied local artwork is a separate input. The terms also require an application non-affiliation/trademark notice and linked "Data provided by Discogs" attribution beside imported source data; these requirements are not limited to a future public release. Public distribution adds concerns about bundled images/data and Restricted Data transfer or commercial use. [API Terms of Use](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use)

The CC0 grant supplies the copyright/database-rights basis for durable reuse of covered metadata. The [current general terms](https://support.discogs.com/hc/en-us/articles/360009334333-Terms-of-Service), updated 2026-02-23, also distinguish [CC0 data dumps](https://data.discogs.com/) from API Service Data. A dump-derived local index is an alternative, but the owner has chosen the public REST path with permanent CC0 tags. The API source-preview versus local-tag interpretation is documented in the decision, rather than held open as a required provider reply. No repeated legal prompt or automated expiration of saved tags is part of this model.

## Authentication and operating limits

The recorded search, release, master and versions requests returned <code>200</code> without authorization. Use those public requests for the initial personal app, as directed by the owner. This does not guarantee permanent anonymous access. The [official client README](https://github.com/discogs/discogs_client/blob/c159195a43ceb3def5a9be2acce43bbad71a2e32/README.mkd) describes search as authenticated and supports user tokens and OAuth 1.0a, but explicitly marks that client deprecated. Its historical guidance is distinct from the current observation. Token setup and authenticated testing are deferred, not completion requirements for issue #19. If authentication is introduced later, validate its request form and store credentials in OS credential storage. No private credentials were used here. See the [access contract](DISCOGS_INTEGRATION_DECISION.md#access-and-credential-contract).

Mp3tag's current documentation uses a browser-based Discogs authorization flow: sign in, approve Mp3tag, then enter the code shown in the browser. Its import flow is explicitly per album. The user searches, selects a result, reviews fields and cover art, may reorder the track-to-file mapping, then confirms the import. This is a good behavioral reference, though Mp3tag's OAuth requirement is not evidence that every public read request must be authenticated. [Mp3tag Discogs authorization](https://docs.mp3tag.de/tag-sources/discogs-auth/), [Mp3tag online tag import](https://docs.mp3tag.de/tag-sources/import/)

Send a descriptive <code>User-Agent</code> with every request. All ten recorded API responses returned <code>X-Discogs-Ratelimit: 25</code> with used/remaining headers. The header alone does not establish the time window, and counters did not advance uniformly. The current developer portal returned <code>403</code>; authenticated quota and any separate image allowance remain unverified. Do not treat the customary 60/minute value as a tested entitlement. Watch headers, debit requests locally, paginate on demand and avoid a request per track. Handle <code>429</code> with bounded backoff and valid <code>Retry-After</code> information when supplied. No live 429 was triggered; the probe's synthetic test verifies only that capture stops after one. [Rate limiting reference](https://www.discogs.com/developers#page:home,header:home-rate-limiting)

For a typical album import, the app needs one search request and one release request. Fetch master versions only when the user asks to browse editions. Handle network errors, 401/403, 404, and 429 without altering files. A deleted or inaccessible release ID should return the user to search; rate limiting should defer the lookup; network failures should leave the staged proposal untouched.

## Recommended album workflow and safe writes

1. Let the user select the files for one album. Show the count and existing album/artist values so mixed albums are visible.
2. Search once with artist and release title. Offer barcode or catalog number as optional refinements. Present candidates with country, year, format, label/catalog number, master link, and result preview. Never silently choose the first result.
3. Fetch the chosen release. Show its release ID, full tracklist, edition details, credits, and available images. Use the master versions list only if the user wants to compare editions.
4. Show local files beside the Discogs tracks. Let the user drag files into order or move them up and down. Display unmatched files, extra Discogs tracks, headings, index rows, missing durations, and per-track artist credits. Offer title or duration sorting only as suggestions.
5. Let the user choose fields to replace and fields to keep. Treat album-level fields as apply-to-all for the selected set; keep title, track artist, track number, and disc number per file. Make artwork a separate opt-in operation.
6. Stage every edit before writing. Validate the whole mapping and each target file first. Keep a per-file backup or equivalent recovery path. A batch of files cannot be one filesystem transaction, so report each successful and failed file, offer retry for failed files, and do not report full success after a partial write. A failed image write should not silently hide whether metadata writes succeeded.
7. For reimport, retain the selected release ID and source link as provenance under the chosen model. Reopen that exact release and present a fresh diff; do not reapply old search results or overwrite fields the user did not select. Avoid duplicate embedded covers on retry.

For a CUE sheet that describes several virtual tracks inside one audio-image file, the container has one tag set and one embedded artwork set. Treat it as one album-level write target; do not claim that Discogs track metadata was written independently to each virtual track. Preserve the CUE sheet unless CUE editing is a separately reviewed feature. If the CUE points to separate audio files, map and write those physical files individually. Embed in selected files, Save beside files and Both remain separate destinations for local or otherwise permitted images. The owner's updated source decision excludes Discogs embedding; do not apply the older specification wording to reintroduce it.

## Acceptance cases

- A broad search returns several releases and a master. The user can inspect the edition details and choose the exact release.
- Searching by barcode narrows results but still permits multiple editions.
- A two-disc CD maps positions such as <code>1-1</code> and <code>2-1</code> to disc and track numbers without losing release order.
- A vinyl release with positions <code>A</code>, <code>B</code>, <code>A1</code>, or <code>B2</code> preserves the side notation and does not create bogus numeric tracks.
- <code>heading</code> and <code>index</code> rows appear in the preview but are not treated as files. Nested <code>sub_tracks</code> retain their grouping, and combined/split movements require review.
- A compilation preserves the album artist separately from available per-track artist credits.
- Missing duration remains missing. A populated duration does not overwrite actual file length or prove it was printed.
- Missing images, blank search thumbnails, secondary covers, and different image dimensions are handled without assuming a high-resolution front cover exists.
- A 429, network error, or file-write failure leaves the staged import reviewable and reports exactly what was written.
- A single-file CUE image receives one container-level write; a multi-file CUE can map to its physical audio files.
- Reimporting a selected release does not duplicate artwork or overwrite fields excluded in the preview.
